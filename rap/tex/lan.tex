\section{Getting to a language}\label{sec:lan}
This section describes the process, the steps, and the considerations for
designing the risc-v styled typed assembly language suited for static
worst-case execution time analysis.
Only a subset of the idea of the language will be fully fleshed out, and an
even smaller part implemented.
The \say{full} language requires much too complex typing that involves
constraint satisfaction of predicate logic, far out of the scope of this
project, unfortunately.
\say{The language} refers to the implementation TAL designed for WCET.
The language syntax is pictured in figure \ref{syn:my-tal}.
All registers map to $\tau$, except when otherwise noted. The register names
follow the risc-v ABI names\cite{cod}.
If a register is not explicitly typed, it will default to \ttop.
The jump instruction \jump is kept only to link blocks together, mimicking
assembly fall-through.

\subsection{Strays from risc-v}
As with the TALs introduced above, there is little reason to distinguish
between immediate instructions and register instructions, meaning that \subi
and \sub can be treated the same. This is due to the value type that they all
share in some form, defined in some way as
\begin{equation*}
    \begin{array}{llcl}
        \text{value}      & v     & ::= & c \mid r \\
    \end{array}
\end{equation*}
For code generation, these will have to be reintroduced, but this is trivial,
since the value field will either be an immediate value or a register.

Since all types are word sized, we replace the load and store instructions with
$\load\ r_d,\ imm(r_s)$ and $\store\ r_s,\ imm(r_d)$

% The \mv instruction also differs here, because it also works as a complete load
% immediate instruction.
% The code gen will depend on whether $v$ is a value or a register.
% Code generation in the case of register is as expected.
% If it is a value, then it expands to the \var{lui} + \var{addi} construct.
Two very specific instructions are also added: \mvscratch and \mvshared. They
serve a very specific purpose in moving the start address of either the
\scratch or \shared memory regions into register $r_d$.
Initially I did not want to stray from risc-v, so using a combination of
\var{lui} and \var{addi}, however that would create an incomplete type between
the two instructions.
For a while, the second operand of \mv could be a value type $v$, which would
then be translated to \var{lui} and \var{addi} if the type of $v$ called for it.
But still, magic values for the memory region pointers were needed.
This is the problem \mvscratch and \mvshared attempt to solve, however ugly it
may be.

\subsection{Types}
While the syntax of the language is inspired by DTAL, it is much simplified (or
mangled, even).
This is also the case of the $\tau$ types, where only $a$, \ttop, $int$, and
$int(i)$ remain. The array and stack types are still present but wrapped, but
collections will be explained later.
Universally quantified types, i.e. type variables are still present, although
they do not serve a concrete function. Stack type variables are still present.
They are needed to append to a stack, which is needed for \incr.
Specific for the language, region memory type variables have been introduced.
They allow labels to be polymorphic over regions. This is an ergonomic must, as
otherwise the programmer (or a compiler) would have to write labels for both
\scratch and \shared.

For the register file, this also means that any type that is not explicitly
typed defaults to \ttop. This means that for later blocks, \ttop can freely be
coerced into a new type.

The dependent type $int(x)$ where $x$ is an index expression has been
reintroduced as $int(i)$ to allow static evaluation of stack types in \incr and
\decr.
The instructions need to add the right amount of types to the head of the
stack.
It follows that they should only allow immediate values.
This is reflected in their evaluation rules and typing rules in figure
\ref{fig:eval-rules} and figure \ref{fig:typing-rules-values}, respectively.

The type variable context strays from the inspiration (DTAL) by essentially a
set of bindings. The inspiration comes from the hindley-milner
algorithm\cite{pldi}.
This choice also has a big implication on the type equality and coercion rules,
as these now produce a side-effect, i.e. they change or add mappings to the
context $\Delta$.
Another implication of this is that it forces the entrypoint to have no type
variables. This makes sense, as there would be no way to deduce the type
information. If for some reason one wanted to explicitly state \say{anything}
one would have to use \ttop.
If $\alpha \in \dom(\Delta)$ then $\Delta{\alpha} = \tau$, and similarly for
$\mu$ and $\rho$.

\subsection{Collections}
This section describes how the array and stack types work with each other, and
how they are to be thought of conceptually in the language moving forwards.
Some TALs introduce \malloc or similar pseudo-instructions to introduce a
notion of types to arrays. Since assembly does not in of itself contain arrays,
but only pointers, some level of abstraction needs to be introduced for a type
system to be able to type arrays and differentiate them from garbage and labels.
In \texttt{C}, heap arrays are pointers, and pointer arithmetic is allowed.
Labels can only be used in \texttt{goto} statements, and not even arithmetic is
permitted on them. Still, it is not trivial whether \lstinline{float* n} points
to a scalar, or is an array.

\subsubsection{Stacks}

Stack types can be defined recursively as
\begin{equation*}
    \begin{array}{llcl}
        \text{stack types variables}    & \rho  & & \\
        \text{stack types}              & S     & ::= & [] \mid \rho \mid \tau :: S \\
    \end{array}
\end{equation*}\cite{xi-dtal}

In DTAL, the stack type is a part of the type state $\Sigma$, and is modified
through \texttt{pushd} and \texttt{pop} operations, a very conventional way to
use the stack.
Here, stacks are used not only for the call-stack, but general allocations, and
to be coerced into array types.
To communicate to the type system that we intend to modify a stack, we
introduce two instructions \incr and \decr. They may be described through the
code generation in \ref{fig:incr-codegen}. \incr decreases the stack pointer in
$r_s$ by $v$ words (removing the need for runtime alignment) and places the
value in $r_d$ whose types will be that of $r_s$ with $v$ \ttop values
appended to it, e.g.,
\begin{lstlisting}[gobble=4]
    main:   ('r)
            [sp: 'r]
            incr    a0, sp, 4   ; a0 : top :: top :: top :: top :: 'r
\end{lstlisting}
where \lstinline{'r} is a stack type variable.
\decr functions as expected, popping $v$ words off the stack.

A programmer may not be interested in passing on \emph{the whole} stack after
increasing the word count, such as stack arrays in C. If the type of a stack
allocated array was the whole call-stack, not only would it obfuscate the
intend, it would prevent memory safety (if the type system enforced such
things).
It is therefore desirable to \say{cut down} or slice a stack. This can be done
by considering a stack $S$ a subtype of a stack $S'$ if $S$ is contained within
$S'$ with a possibly empty tail. Or formally
\begin{equation*}
    \tau_0 \cons \cdots \cons \tau_n
    \leq
    \tau_0 \cons \cdots \cons \tau_m
    \mid
    n \leq m
\end{equation*}

To illustrate the usefulness, we can expand on the previous code snippet:
\begin{lstlisting}
    main:   ('r)
            [sp: 'r]
            incr    a0, sp, 4   ; a0 : top :: top :: top :: top :: 'r
    subtype:
            [a0: top :: top :: top :: top]
            ..
\end{lstlisting}

While \ttop is not so useful in of itself since it practically refers to
garbage values, we will later introduce a subtyping rule to \ttop, specifically
such that any type can be coerced from \ttop.
This makes it possible to instantiate a stack of any type (although the
language may not support so many types) without introducing special \say{typed}
syntax to \incr and \decr, as DTALs $newarray[\tau]$.
So really we could write:
\begin{lstlisting}
    main:   ('r)
            [sp: 'r]
            incr    a0, sp, 4   ; a0 : top :: top :: top :: top :: 'r
    subtype:('a)
            [a0: 'a :: 'a :: 'a :: 'a]
            ..
\end{lstlisting}
for some type variable \var{'a}.

Since we have foregone array initialization instructions, we add the choice to
coerce a stack containing only one type to an array of that type. This models C
stack arrays quite well.

\subsection{Abstract machine}
    Unlike other TAL abstract machines, I am omitting the stack, since it will
    be used as a normal register (\var{sp}).
    The DTAL abstract machine has a machine state $\mathcal M$ $(\mathcal H,
    \mathcal R, \mathcal S)$ being a triple over a heap, register file, and
    stack.
    Since the system the language is targeted at is stack based, no heap is
    needed (except for program text, but this is omitted partially due to
    program scope) and no explicit stack is needed, since the register \var{sp}
    will be used.
    A such, the abstract machine contains only a finite mapping
    between registers and values.

    This is also the motivation behind removing the DTAL type state $\Sigma$
    and state type $\sigma$.

\subsection{Dynamic Semantics}
Dynamic semantics is needed to evaluate the types throughout block execution
for reasons discussed in section (TODO: REF IDEAS -- WHY NOT TRANSITIONS).

Since we are explicit in the use of \var{sp} the abstract machine does not need
to keep track of this.
The heap is also omitted. We instead refer to hardcoded values: the start of
each memory region.
This means that
\begin{lstlisting}
    start:
            mv      a0, SCRATCH_START
\end{lstlisting}
will set the type of \var{a0} in the register file to $\scratch S$, where
\var{SCRATCH\_START} refers to an immediate value that points to the start of
the scratch region.
An abstract machine state $\mathcal M$ naturally reduces to just the register
file.
We define $\mathcal M = \mathcal R$ where $\mathcal R(r)$ is a constant.

Similar to the treatment in DTAL, we introduce an instruction sequence $J_P$ of
a program $P$, and $I_B$ for the instruction sequence in $B$ as
\begin{equation*}
    J_P = {l_1; I_{B_1}; \cdots \ ; l_n; I_{B_n}}
\end{equation*}
We use $J_P(i)$ to refer to the $i$th instruction or label in $J_P$. If it is
clear what $P$ is being referred to, we may omit the subscript.
We also use $J_P^{-1}(l) = i \iff J_P(i) = l$ from DTAL.

A $P$-snapshot\cite{xi-dtal} is either \halt or a tuple $(ic, \mathcal M)$ such
that $0 \leq ic < length(J_P)$, where $ic$ is the instruction counter.
$(ic, \mathcal M) \rightarrow_P (ic', \mathcal M')$ means that the machine
state $\mathcal M$ transforms into $\mathcal M'$ by executing the instruction
at $J_P(ic)$. Similarly $ic'$ is incremented or replaced in the case of \jump.

\begin{equation*}
    \mathcal M(v) =
    \left\{
        \begin{array}{ll}
            i               & \text{if $v$ is integer $i$} \\
            l               & \text{if $v$ is label $l$} \\
            C               & \text{if $v$ is collection $C$} \\
            \mathcal R(r)   & \text{if $v$ is register $r$}

\subsection{Static Semantics}
The typing rules for the language is the most important step in the solution of
calculating worst-case execution time with the method discussed.

One difference between other TALs and especially how values $v$ in DTAL and how
they behave here, is that we need a way to instantiate the region memory types.
Earlier instantiating was presented as 

In figure \ref{fig:typing-rules} presenting the typing rules, $\rho_{scratch}$
and $\rho_{shared}$ represent two stack types.
Each region should be defaulted to \ttop, and the amount depends on the
physical size. Since the scratchpad is 128KB\cite{sigma}, $\rho_{scratch}$ may
be defined as $\ttop_1 \cons \cdots \cons \ttop_{128 / w \cdot 1000} \cons
\emptystack$ where $w$ is the machines wordsize.

The type rules for values in figure \ref{fig:typing-rules-values} depend on the
label mapping $\Lambda$ for typing labels. This is the meaning of the notation
$\vdash_\Lambda$, where $\Lambda$ is a label mapping function.
In practice, only one label mapping function will be used, so for brevity
$\vdash$ may be used --- like in DTAL.

The typing rules for arithmetic instructions follow from \add in figure
\ref{fig:typing-rules}.

The typing for jumps \jump do not continue checking the instructions of the
target block.
It checks if the current state aligns with the state type $\sigma$ in the
target block.
This means comparing each register type. This is explained in section
\ref{sec:type-eq-co}.
Since the handling of stacks and arrays rely heavily on subtyping, we use the
coercion rules for comparison or acceptance of a new state type.

The type rules differ from DTAL in that they use and (potentially) \emph{update} the type variable context $\Delta$.
This is specifically for variable typing rules.
The motivation for this choice is jumps, going from one machine state to
another.
To make use of the ergonomics discussed earlier in regards to handling stacks
and arrays, a machine state $M$ consisting of a register file and variable
mapping can jump to $M'$ iff $M$ can be coerced into $M'$.
Or in other words
\begin{equation*}
    \Delta, R \models_c R' \leadsto \Delta'
\end{equation*}
When adding a binding to a type variable context, we do not want to
accidentally define circular types such as $\alpha \colon \beta,\ \beta \colon
\alpha$.
This is why the variable type equality and coercion do not have rules for other
variables, and as a consequence, type variable contexts can only have a depth
of one, if one were to imagine $\Delta$ as a graph.
This is not dissimilar in the treatment of existential qualifiers\cite{lics},
in the sense of a graph.

Because of this constraint type variables cannot refer to other type variables,
when we coerce register files we can assert that at type-coerce-regfile,
type-reg will never evaluate to a type variable. This means that there is no
need to check if variables in the two register files are unique, or in other
words, we do not have to create fresh variables, something that is required for
hindley-milner type inference\cite{pldi}.

\subsection{Type Equality and Coercion} \label{sec:type-eq-co}
We start by introducing the type equality and coercion rules.

The typing rules for collection types contain a lowercase c $c$, which is
taken to mean the pattern matched type of either $\tau\ array(i)$ or $S$.

The coercion rules allow the type variable context to be modified, by coercing
type variables into types.
The use case is limited to state transitions, i.e. jumps. This is the part that binds type variables to types, specifically
\begin{equation*}
    \infer
        {\Delta; R \models_c R' \leadsto \Delta_n}
        {
            % \Delta; R \vdash r_1 : \tau_1 &
            % \emptytv; R' \vdash r_1 : \tau'_1 &
            % \emptytv \models \tau'_1 \leq \tau_1 \leadsto \Delta_1 &
            % \cdots &
            \Delta; R \vdash r_n : \tau_n &
            \Delta_{n - 1}; R' \vdash r_n : \tau'_n &
            \emptytv \models \tau'_n \leq \tau_n \leadsto \Delta_n
        }
\end{equation*}
where $\Delta_n$ is created through accumulating type captures starting at
$\Delta_1 = \emptytv$ for all $n$ registers.

Since I decided to reflect the risc-v register ABI names in the syntax of the
language, it is not actually possible to iterate over all registers. Not for
any semantic reasons. Therefore I informally introduce $r_n$ to be a register,
and the above meaning is that it iterates over all ($n$) registers.
